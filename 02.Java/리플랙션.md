## 1. 리플렉션(Reflection)의 정의

**리플렉션**은 구체적인 클래스 타입을 알지 못하더라도 **런타임(Runtime, 애플리케이션 실행 중)에 클래스, 메서드, 필드에 직접 접근하여 정보를 분석하고 조작할 수 있는 자바 API**입니다.

보통 자바 코드는 컴파일 시점에 타입이 결정되지만, 리플렉션을 사용하면 컴파일 이후에 동적으로 객체를 생성하거나 메서드를 호출하는 "동적 프로그래밍"이 가능해집니다.

---

## 2. 리플렉션으로 할 수 있는 것

리플렉션을 사용하면 클래스의 '내부 정보'를 완전히 들여다볼 수 있습니다.

- **클래스 정보 확인:** 클래스명, 부모 클래스, 구현한 인터페이스, 어노테이션 등 확인.
- **생성자 접근 및 객체 생성:** `new` 키워드 없이도 클래스 이름만으로 인스턴스 생성.
- **필드 읽기 및 수정:** 심지어 `private`으로 선언된 필드도 강제로 접근하여 값을 바꿀 수 있음.
- **메서드 실행:** 이름만 알고 있다면 어떤 메서드든 실행 가능.
---

## 3. 리플렉션의 실제 활용 사례

우리가 일상적으로 쓰는 많은 프레임워크가 리플렉션 덕분에 존재합니다.

1. **Spring Framework:** `@Service`, `@Autowired`가 붙은 클래스를 찾아 빈(Bean)으로 등록하고 의존성을 주입할 때 사용합니다.
2. **JPA (Hibernate):** 객체와 DB 테이블을 매핑하고, 기본 생성자를 통해 엔티티 객체를 생성할 때 사용합니다.
3. **Jackson (JSON 라이브러리):** JSON 데이터를 자바 객체로 변환할 때 리플렉션을 사용해 필드에 값을 넣어줍니다.
4. **JUnit:** `@Test` 어노테이션이 붙은 메서드들만 골라서 실행할 수 있는 이유도 리플렉션 덕분입니다.
---

## 4. 리플렉션의 치명적인 단점 (면접 핵심 답변)

면접관이 "리플렉션이 좋은데 왜 남발하면 안 되나요?"라고 묻는다면 반드시 이 답변을 하세요.

- **성능 저하:** 리플렉션은 JVM의 최적화(JIT 컴파일러 등)를 방해하며, 직접 코드를 실행하는 것보다 훨씬 느립니다.
- **컴파일 시점의 타입 체크 불가:** 코드에 오타가 있어도 컴파일 시점에는 에러가 안 나고, 실제 실행할 때(Runtime) 프로그램이 터집니다 (`NoSuchMethodException` 등).
- **캡슐화 파괴:** `private` 멤버에 강제로 접근할 수 있어, 객체지향의 핵심 원칙인 캡슐화를 저해하고 보안 문제를 일으킬 수 있습니다.
---
## 5. 면접 모범 답안 예시

> **면접관:** "자바의 리플렉션(Reflection) API에 대해 설명해 주세요."
> 
> **답변:** "리플렉션은 런타임에 클래스의 메타데이터를 분석하고 조작할 수 있는 API입니다. 클래스 이름만 알아도 객체를 생성하거나 private 필드에 접근하는 등의 동적인 작업이 가능합니다. 주로 **스프링의 의존성 주입(DI)**이나 **JPA의 엔티티 매핑**처럼 프레임워크가 개발자의 코드를 동적으로 처리해야 할 때 사용됩니다. 하지만 성능 오버헤드가 발생하고 컴파일 시점의 타입 안정성을 보장받지 못한다는 단점이 있기 때문에, 일반적인 비즈니스 로직에서는 사용을 지양하고 프레임워크 수준에서 활용하는 것이 적절합니다."
