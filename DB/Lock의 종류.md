### 1. 동작 방식에 따른 분류 (가장 중요)
- 낙관적 락 (Optimistic Lock): 충돌이 안 날 거라고 믿고, 마지막에 **버전**을 확인하는 방식 (DB 기능이 아닌 애플리케이션 레벨). ^bd306c
- 비관적 락 (Pessimistic Lock): 충돌이 날 거라고 가정하고, **데이터 읽기 시점부터 실제 락**을 거는 방식 (DB의 `FOR UPDATE` 등).
    
---
### 2. 권한(공유 여부)에 따른 분류 (DB 기본)
데이터베이스 내부에서 실제로 자원을 점유할 때 사용하는 분류입니다.
- 공유 락 (Shared Lock / S-Lock): "나 읽고 있으니까 아무도 수정하지 마." (읽기 가능, 쓰기 불가능), 일반적인 SELECT는 격리 수준에 따라 락을 잡지 않는다.
- 배타 락 (Exclusive Lock / X-Lock): "나 수정하고 있으니까 아무도 건드리지 마." (읽기/쓰기 모두 불가능), INSERT,UPDATE,DELETE 쿼리 실행 시 DBMS가 자동으로 해당 ROW에 베타 락을 건다. 조회 시점에 미리 락을 선점하려면 SELECT ... FOR UPDATE를 사용한다.

---
### 3. 락의 범위(Granularity)에 따른 분류

어디까지 잠글 것인가에 대한 분류입니다. 이 범위에 따라 성능과 정합성이 결정됩니다.
- **데이터베이스 락:** DB 전체를 잠금 (거의 안 씀)
- **테이블 락:** 테이블 전체를 잠금 (DDL 수행 시 발생): 주로 DDL(테이블 구조 변경) 작업을 할 때 자동으로 발생한다. 전체 데이터를 마이그레이션하거나 대규모 배치 작업을 할 때 성능을 위해 의도적으로 사용하기도함
- **페이지/블록 락:** 데이터가 저장된 물리적 블록 단위 잠금. 
- **로우 락 (Row Lock):** 특정 행(Row) 하나만 잠금 (**가장 많이 사용됨**). WHERE 절에 인덱스를 사용하여 특정 레코드만 지정한다. 주의) 인덱스가 없는 컬럼을 조건으로 UPDATE 등을 수행하면 DBMS는 어떤 행을 잠글지 몰라 테이블 전체에 락을 거는 대참사가 발생할 수 있다.

---
### 4. [심화] 분산 환경에서의 락

만약 서버가 여러 대라면, 한 서버 내의 락(Java의 `synchronized` 등)은 무용지물이 됩니다. 이때 사용하는 방식입니다.
- **분산 락 (Distributed Lock):** Redis나 Zookeeper 같은 외부 저장소를 이용해 여러 서버가 공통된 락을 공유하는 방식입니다.
    
---

> "락은 기준에 따라 다양하게 분류됩니다. 크게는 충돌을 대하는 전략에 따라 낙관적/비관적 락으로 나뉘고, DB 내부 운영 관점에서는 공유/배타 락으로 나뉩니다. 실무에서는 보통 로우(Row) 단위의 락을 주로 활용합니다."


### 실무에서 개발자가 락을 설정하는 구체적인 레이어
1단계 : 데이터베이스 격리 수준 설정
		전체적인 락 전략의 기본 값을 정한다. 격리 수준을 높일수록 DBMS가 더 엄격한 락을 자동으로 관리한다
2단계 : 쿼리 레벨에서의 명시적 잠금. 개발자가 쿼리에 직접 명시
3단계 : 애플리케이션 레벨 (JPA 등)
Java Spring 환경이라면 어노테이션으로 편리하게 설정합니다.

Java

```
// 비관적 락 설정 (DB의 FOR UPDATE 쿼리 생성)
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select m from Member m where m.id = :id")
Member findByIdForUpdate(Long id);
```
